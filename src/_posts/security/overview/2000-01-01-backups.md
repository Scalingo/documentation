## English {#en}

### Managed database backups

Backup methods, retention, and recovery options depend on the database engine, architecture, and service class. Backups
handled by Scalingo are encrypted. See the current [database backup policy][backup-policies] for details and its
[restore guides for each database engine][restore-guides].

### Testing a restore

Scalingo regularly tests whether its backups can be restored. You should also periodically test your own recovery procedure
using a separate database, then verify that the restored data and application behave as expected. Prefer a sanitized
test dataset; if you restore production data, apply the same access restrictions and retention requirements to the test
copy. The exact process depends on the database engine; see the [database copy guide][database-copy] and the
[engine-specific restore guides][restore-guides].

For PostgreSQL Shared Resources, Point-in-Time Recovery (PiTR) restores the selected database and requires it to be
stopped. To test a restore on a separate target, restore a logical backup or dump instead. Deleting a database does not
immediately remove its scheduled logical backups; they expire according to the retention policy. Deletion permanently
removes continuous backup data. Review the [backup policy][backup-policies] before using sensitive data in a test.

If the test uses health data subject to HDS requirements, enable HDS coverage when creating every target resource that
stores or processes the data; coverage cannot be enabled later. See the [HDS resource requirements][hds-resources].

Backup and PiTR status events are available through [app notifiers][notifiers] and are listed in the
[backup policy][backup-events].

### Application and external storage

The filesystem in an application container is temporary. Use an [external storage service][filesystem] for files that
must persist. Database backups do not include files stored with an external provider; arrange those backups with the
provider.

## Français {#fr}

### Sauvegardes des bases de données managées

Les méthodes de sauvegarde, la rétention et les options de restauration dépendent du moteur de base de données, de
l'architecture et de la classe de service. Les sauvegardes prises en charge par Scalingo sont chiffrées. Consultez la
[politique de sauvegarde des bases de données (en anglais)][backup-policies] et ses
[guides de restauration pour chaque moteur (en anglais)][restore-guides].

### Tester une restauration

Scalingo vérifie régulièrement que ses sauvegardes peuvent être restaurées. Nous vous recommandons également de tester
périodiquement votre propre procédure de reprise sur une base de données distincte, puis de vérifier le comportement des
données restaurées et de l'application. Privilégiez un jeu de données de test expurgé des données qui ne sont pas nécessaires ; si vous restaurez des données
de production, appliquez à la copie les mêmes restrictions d'accès et règles de conservation. La procédure exacte dépend
du moteur ; consultez le [guide de copie d'une base de données (en anglais)][database-copy] et les [guides de
restauration propres à chaque moteur][restore-guides].

Pour PostgreSQL sur ressources partagées (Shared Resources), la restauration à un instant donné (PiTR) s'applique à la
base sélectionnée et nécessite son arrêt. Pour tester une restauration sur une cible distincte, restaurez plutôt une sauvegarde logique ou un dump.
La suppression d'une base de données ne supprime pas immédiatement ses sauvegardes logiques planifiées ; elles expirent selon
la politique de rétention. La suppression efface définitivement les données de sauvegarde continue. Consultez la
[politique de sauvegarde][backup-policies] avant d'utiliser des données sensibles pour un test.

Si le test utilise des données de santé soumises aux exigences HDS, activez la couverture HDS lors de la création de toute
ressource cible qui stocke ou traite ces données ; elle ne peut pas être activée ultérieurement. Consultez les [exigences
des ressources HDS (en anglais)][hds-resources].

Les événements de statut des sauvegardes et du PiTR sont disponibles via les [notifiers applicatifs (en anglais)][notifiers]
et sont répertoriés dans la [politique de sauvegarde (en anglais)][backup-events].

### Stockage applicatif et externe

Le système de fichiers d'un conteneur applicatif est temporaire. Pour conserver durablement des fichiers, utilisez un
[service de stockage externe (en anglais)][filesystem]. Les sauvegardes des bases de données n'incluent pas les fichiers
stockés auprès d'un fournisseur externe ; prévoyez ces sauvegardes avec le fournisseur.
