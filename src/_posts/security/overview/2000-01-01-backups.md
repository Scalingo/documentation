## English {#en}

### Managed database backups

Backup methods, retention periods, and recovery options depend on the database engine, architecture, and service class.
Scalingo encrypts the backups it handles. See the current [database backup policy][backup-policies] and its
[engine-specific restore guides][restore-guides].
You can monitor backup and PiTR status with [application notifiers][notifiers]; the backup policy lists the available
events.

### Backup Testing

Scalingo regularly tests the backups it manages by restoring them in a separate environment and checking data integrity
and application behavior. Test your own recovery procedure periodically on a separate database, then check that the
restored data is correct and the application works as expected. Use sanitized test data where possible. If you restore
production data, apply the same access restrictions and retention requirements to the test copy. Steps vary by database
engine; see the [database copy guide][database-copy] and the
[engine-specific restore guides][restore-guides].

On PostgreSQL Shared Resources, Point-in-Time Recovery (PiTR) restores the selected database and requires it to be
stopped. To restore to a separate target, use a logical backup or dump. See the [restore guide][pitr-guide]. Review the
[backup policy][backup-policies] for retention and deletion behavior before using production data in a test.

If the restore target needs to fall within Scalingo's HDS-certified scope, create it using resources eligible for that
scope. Enable HDS when creating the application or a Dedicated Resources database; eligible Shared Resources database
add-ons inherit coverage from their HDS application. Coverage cannot be added to an existing resource. These conditions
define Scalingo's coverage scope; they do not determine whether your organization meets its own regulatory obligations.
See the [HDS resource requirements][hds-resources].

### Application and external storage

Application container files are temporary; see the [external storage guide][filesystem]. Backups of managed databases do
not include files stored with an external provider, so arrange backups for that storage with its provider. For database
backup methods marked as customer-managed, arrange their execution and retention with an external tool as described in the
[backup policy][backup-policies].

## Français {#fr}

### Sauvegardes des bases de données managées {#sauvegardes-des-bases-de-donnees-managees}

Les méthodes de sauvegarde, leur durée de conservation et les options de restauration varient selon le moteur, l'architecture
et la classe de service. Scalingo chiffre les sauvegardes qu'il prend en charge. Consultez la
[politique de sauvegarde des bases de données (en anglais)][backup-policies] et ses
[guides de restauration pour chaque moteur (en anglais)][restore-guides].
Les [notifications applicatives (en anglais)][notifiers] permettent de suivre l'état des sauvegardes et du PiTR ; la
politique répertorie les événements disponibles.

### Tests de sauvegarde

Scalingo teste régulièrement les sauvegardes qu'il gère en les restaurant dans un environnement distinct et en vérifiant
l'intégrité des données et le fonctionnement de l'application. Testez aussi régulièrement votre procédure de restauration
sur une base distincte, puis vérifiez les données restaurées et le fonctionnement de l'application. Utilisez si possible
un jeu de test expurgé des données non nécessaires. Si vous restaurez des données de production, appliquez à la copie les mêmes
restrictions d'accès et règles de conservation. Les étapes varient selon le moteur ; consultez le
[guide de copie d'une base de données (en anglais)][database-copy] et les [guides de restauration propres à chaque moteur (en anglais)][restore-guides].

Avec PostgreSQL sur Shared Resources, PiTR restaure la base sélectionnée et nécessite son arrêt. Pour restaurer sur une
cible distincte, utilisez une sauvegarde logique ou un dump. Consultez le [guide de restauration PostgreSQL (en anglais)][pitr-guide].
Avant d'utiliser des données de production pour un test, vérifiez les règles de conservation et de suppression dans la
[politique de sauvegarde][backup-policies].

Si la cible de restauration doit relever du périmètre HDS certifié de Scalingo, créez-la avec des ressources éligibles à ce
périmètre. Activez HDS à la création de l'application ou d'une base de données Dedicated Resources ; les add-ons de base de
données Shared Resources éligibles héritent de la couverture de leur application HDS. Cette couverture ne peut pas être
ajoutée à une ressource existante. Ces règles définissent le périmètre couvert par Scalingo, mais ne déterminent pas si
votre organisation satisfait à ses propres obligations réglementaires. Consultez les
[exigences des ressources HDS (en anglais)][hds-resources].

### Stockage applicatif et externe

Les fichiers des conteneurs applicatifs sont temporaires ; consultez le [guide du stockage externe (en anglais)][filesystem].
Les sauvegardes des bases managées n'incluent pas les fichiers hébergés par un fournisseur externe ; organisez la sauvegarde
de ce stockage avec son fournisseur. Pour les méthodes de sauvegarde indiquées comme gérées par le client, organisez leur
exécution et leur conservation avec un outil externe, comme l'indique la [politique de sauvegarde (en anglais)][backup-policies].
